# Cortex v0.2.0 Dogfood Report — Operational Evidence Gate

> **Classification**: Controlled Synthetic Workload Profiling
> **Date**: 2026-08-10
> **Author**: Automated Dogfood Harness (`examples/repo_auditor/dogfood_harness.py`)

> [!IMPORTANT]
> This report measures **Cortex runtime framework overhead** using synthetic workloads.
> The Repo Auditor plugins produce simulated results — they do NOT perform real repository
> analysis. All measurements reflect event bus propagation, EventStore journaling, capability
> enforcement, and replay determinism costs. Do not interpret these as repository analysis benchmarks.

---

## 1. Executive Summary

Five controlled synthetic workload profiles were executed through the Cortex v0.2.0
Repo Auditor pipeline to measure framework operational characteristics. The profiles
ranged from 3 steps (baseline) to 200 steps (stress), plus a dedicated capability
enforcement violation path.

**Key Findings**:
- Event throughput sustained **600–2,300 events/sec** across all workload sizes
- Python memory allocation scaled **linearly** from 0.07 MB (3 steps) to 2.61 MB (200 steps)
- Trace persistence scaled linearly: 6.4 KB (3 steps) to 351 KB (200 steps)
- Deterministic replay equivalence **proven for 100% of profiles**
- Capability enforcement correctly rejected unauthorized operations with zero false permits
- The single-process in-memory architecture shows **no bottleneck** at these workload scales

## 5. Scaling Analysis

### 5.1 Execution Time

| Transition | Step Increase | Time Increase | Ratio |
|:--|--:|--:|--:|
| Minimal → Standard | 3.3× | 1.0× | Sub-linear |
| Standard → Large | 5.0× | 3.6× | Sub-linear |
| Large → Stress | 4.0× | 4.8× | Approximately linear |

Execution time growth is **approximately linear** with step count at the stress level.
The sub-linear behavior at smaller scales suggests fixed overhead dominates.

> [!NOTE]
> Five data points are insufficient to determine asymptotic complexity with confidence.
> These observations describe measured trends, not proven complexity bounds.

### 5.2 Event Throughput

Throughput ranged from **611 to 2,345 events/sec**. The lower minimal-profile throughput
is explained by fixed registration overhead amortized over fewer events. At scale (50+ steps),
throughput stabilizes around **1,900–2,300 events/sec**, indicating the event bus is not
saturating at these workload sizes.

### 5.3 Memory (Python Allocations)

| Profile | Peak Traced (MB) | Steps | MB per Step |
|:--|--:|--:|--:|
| Minimal | 0.073 | 3 | 0.024 |
| Standard | 0.153 | 10 | 0.015 |
| Large | 0.670 | 50 | 0.013 |
| Stress | 2.614 | 200 | 0.013 |

Memory scales **linearly** at ~13 KB per step (Python allocations only, measured via
`tracemalloc`). This does NOT represent total process RSS. At 200 steps, peak Python
allocation is 2.6 MB — well within single-process capacity.

**Extrapolation** (for reference only, not a guarantee): A 10,000-step workload would
allocate approximately 130 MB of Python objects, still manageable in a single process.

### 5.4 Trace Persistence

| Profile | Events | Trace Size (KB) | Bytes per Event |
|:--|--:|--:|--:|

Trace size scales **linearly** at ~597 bytes per event. This is the dominant I/O cost —
at stress level, trace save (0.47s) exceeds execution (0.31s).

## 6. Capability Enforcement

### Normal Execution Path (Minimal/Standard/Large/Stress)

All 6 requested capabilities were **granted** by the platform:
`workflow.plan.create`, `workflow.command.issue`, `fs:read`, `exec:git`, `exec:pytest`, `hardware.telemetry.read`

Zero violations. Zero denied capabilities. All plugins reached ACTIVE state.

### Violation Path

The violation profile deliberately requested `fs:write` (not granted by the platform).
The `CapabilityNegotiator` correctly:
1. Detected the unauthorized capability request
2. Rejected the operation **before execution**
3. Emitted 3 `CAPABILITY_VIOLATION` events (one per command step)
4. Transitioned the workflow to `FAILED` state

**No unauthorized operations were executed.** The capability sandbox enforced the security
boundary with zero false permits.

## 7. Observed Bottlenecks

Based **solely** on measured data:

| Bottleneck | Evidence | Severity |
|:--|:--|:--|
| **Trace I/O dominates at scale** | At 200 steps, trace save (0.47s) > execution (0.31s). JSON serialization + disk write becomes the slowest phase. | Moderate |
| **Inspect phase scales poorly** | Inspect (0.57s) exceeds all other phases at 200 steps. Causality tree construction appears to have super-linear behavior. | Moderate |
| **In-memory EventStore grows unboundedly** | All events retained in `list[AnyEvent]`. At 602 events, 2.6 MB. At 60,000 events, this would approach 260 MB. | Low (at current scale) |
| **Registration is negligible** | 0.001–0.002s across all profiles. | Not a bottleneck |

> [!NOTE]
> No bottleneck observed that would **require** process isolation at current workload scales.
> The trace I/O and inspect costs are optimization targets that can be addressed within a
> single-process architecture (e.g., binary serialization, lazy inspection).

## 8. v0.3 Evidence Gate — Feature Disposition Table

Classification based **exclusively** on empirical measurements from this report.
Features are classified as:
- **Defer**: No evidence of need. Do not invest engineering effort.
- **Investigate**: Potential benefit observed, but insufficient evidence to mandate. Gather more data.
- **Required**: Clear empirical evidence that the feature is necessary.

| v0.3 Feature | Disposition | Rationale |
|:--|:--|:--|
| **Process Isolation** | **Defer** | Single-process handles 602 events in 1.66s with 2.6 MB memory. No observed contention, deadlocks, or resource exhaustion. Process boundaries add complexity without measured benefit. |
| **IPC Protocol** | **Defer** | No inter-process communication is needed when the single-process model shows no bottleneck. IPC would add latency and failure modes with no measured justification. |
| **Crash Recovery** | **Investigate** | Trace persistence works correctly, but the current model requires full re-execution after crash. If workflows scale to minutes, crash recovery may become valuable. No crash was observed during testing. |
| **Execution Timeouts** | **Investigate** | All profiles completed within 1.7s. No hangs observed. However, real-world plugins performing actual I/O (git, pytest) may exhibit unbounded latency. Worth adding configurable timeouts as a safety net. |
| **Resource Limits** | **Investigate** | Memory growth is linear and predictable (~13 KB/step). At extreme scales (10,000+ steps), unbounded EventStore growth could become problematic. Consider implementing configurable memory caps or event log rotation. |
| **Worker Supervision** | **Defer** | All plugins executed synchronously without errors. No evidence of plugin failure modes requiring supervision trees. Revisit when real I/O plugins are introduced. |
| **Event Bus Optimization** | **Investigate** | Throughput stabilizes at ~2,000 events/sec. Adequate for current use cases but may become limiting with real-world I/O plugins. Consider benchmarking with actual I/O operations before optimizing. |

## 9. Conclusion

The Cortex v0.2.0 single-process, in-memory architecture is **empirically sufficient** for
workloads up to at least 200 synthetic pipeline steps (602 events). No measurement supports
the immediate introduction of process isolation or IPC protocols.

**Recommended next actions**:
1. **Optimize trace I/O** (the dominant bottleneck at scale) — consider binary serialization or streaming writes
2. **Optimize inspect phase** — profile causality tree construction for potential algorithmic improvement
3. **Add configurable timeouts** — safety net for future real-I/O plugins
4. **Revisit process isolation** only after introducing real-world plugins with actual I/O latency and failure modes

> [!IMPORTANT]
> **Evidence Gate Verdict**: The v0.3 multi-process architecture is **NOT required** based on
> current operational evidence. Features #13–#16 should remain in **Defer/Investigate** status.
> Proceed with v0.2.x hardening (Issues #2, #3, #5, #9–#12) before reconsidering v0.3 scope.
